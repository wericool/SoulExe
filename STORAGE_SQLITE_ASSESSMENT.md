# Оценка переноса истории SoulExe с JSON на SQLite

## Текущее состояние

`JsonDataStore` держит весь `SoulDataRoot` в памяти и сериализует его целиком при каждой мутации. Перед обычным сохранением создаётся полная резервная копия, а чтение наружу использует полное JSON-клонирование. Schema v10 хранит разговоры единожды в `Conversations`, однако стоимость чтения, клонирования, резервного копирования и записи всё равно растёт вместе со всей историей, даже если добавлено одно сообщение.

Плюсы текущего решения: минимальная сложность, переносимый и читаемый файл, атомарная замена через `.tmp`, уже работающие миграции и резервные копии. Для небольшой локальной библиотеки это разумнее базы данных.

## Решение

Сейчас SQLite не внедрять. Дублирование старой и канонической моделей уже удалено; JSON остаётся более простым решением, пока фактический объём данных и задержки не достигли измеримых порогов ниже.

Вернуться к миграции, если выполняется хотя бы один из измеримых критериев:

- `soulexe.json` стабильно превышает 25 МБ;
- p95 `STORE SAVE ... elapsedMs` превышает 250 мс на обычной машине пользователя;
- один разговор содержит более 10 000 сообщений либо библиотека — более 100 000 сообщений;
- полное клонирование корня становится заметно в профилировщике или вызывает паузы UI;
- потребуется поиск, пагинация или обновление отдельных сообщений без загрузки всей истории.

## Предлагаемая схема при достижении порога

- `conversations`: метаданные разговора, режим и состояние хода;
- `participants`: персонажи, пользовательские персоны и режиссёр;
- `messages`: последовательность, авторские snapshot-поля, тип, содержимое и время;
- отдельные таблицы для персонажей, персон, лора, summary и Soul Memory;
- индексы `(conversation_id, sequence)` и `(conversation_id, created_at)`;
- WAL, foreign keys и транзакция на один логический ход;
- JSON оставить только для экспорта/импорта и резервной копии.

## Безопасная последовательность будущей миграции

1. Зафиксировать финальную каноническую модель после удаления compatibility-полей.
2. Добавить независимый интерфейс хранилища и оставить JSON-реализацию эталоном.
3. Создать SQLite рядом с JSON, импортировать в одной транзакции и сверить количество разговоров, участников, сообщений и хэши содержимого.
4. Не удалять исходный JSON; переименовать его в датированную миграционную копию только после успешной проверки.
5. Прогнать приложение один релиз с возможностью безопасного отката и только затем прекратить dual-read.
