# Архитектурный аудит SoulExe: разговоры, чаты и сцены

**Статус:** предложение для ветки `testing`. Этот документ не меняет рабочую логику и не требует миграции данных до отдельного решения.

## Краткий вывод

Ваше наблюдение верное: **обычный чат и сцена являются двумя режимами одного доменного объекта — разговора**. В обоих случаях есть история сообщений, участники, контекст, сводка, время последнего изменения, отображение в общей ленте и генерация следующей реплики. Сцена отличается не тем, что это другой продукт, а тем, что у разговора два ИИ-участника, режиссёрские события и политика автоматического хода.

Сейчас это разделение проведено слишком глубоко: существуют разные модели, сообщения, сервисы, контракты API, построители промптов и два экрана Mobile. Из-за этого одна функция часто появляется дважды, а исправление в обычном чате не гарантирует исправление в сцене.

> **Рекомендация:** не склеивать `SoulChat` и `SoulScene` в один большой класс с десятками необязательных полей. Вместо этого нужно ввести общий `Conversation` с участниками, сообщениями и базовым контекстом, а отличие между диалогом и сценой выражать отдельной политикой хода и сценическими настройками.

## Что фактически есть сейчас

| Слой | Обычный чат | Сцена | Последствие |
|---|---|---|---|
| Хранилище | `SoulChat` вложен в `SoulCharacter.Chats` | `SoulScene` лежит в `SoulDataRoot.Scenes` | Один тип разговора имеет владельца-персонажа, второй — корневой список. Общая выборка требует специальной склейки. |
| Сообщение | `SoulMessage`: роль, варианты ответа, вложения, редактирование | `SoulSceneMessage`: вид, спикер, текст | Возможности сообщений расходятся; сцена не получает варианты и вложения автоматически. |
| Контекст | `PromptEngine` | `ScenePromptEngine` | Правила роли, лор, история и обрезка контекста поддерживаются двумя путями. |
| Память | Summary, Soul Memory, состояние, персона пользователя | Отдельный Summary сцены | Новая функция памяти должна решать, в какой из двух подсистем её добавлять. |
| Генерация | `SendAsync`, продолжение, сетевой вызов чата | Несколько методов генерации сцены для Desktop и сети | Потоки генерации и обработка ошибок повторяются. |
| LAN API | `/api/characters/{id}/chats/...`, `/api/chat` | `/api/scenes/...`, `/action`, `/director` | Mobile вынужден держать два набора DTO, экранов и механизмов опроса. |
| UI | `SelectedChat`, `Messages` | `SelectedScene`, `SceneMessages` | В WPF и Mobile одинаковые ленты визуально похожи, но развиваются независимо. |

### Подтверждённые точки дублирования

1. `SoulChat` и `SoulScene` независимо хранят `Id`, `Name`, `SummaryText`, `LastSummarizedSequence`, `Messages`, `CreatedAt`, `UpdatedAt` и `IsPinned`.
2. `CharacterLibraryService` и `SceneService` отдельно реализуют создание, получение, переименование, обновление времени, добавление сообщений, закрепление и удаление.
3. `PromptEngine` и `ScenePromptEngine` оба строят системный контекст, выбирают историю под лимит и нормализуют ролевый вывод, но используют разные модели сообщений и правила.
4. `MainViewModel` имеет независимую логику `GenerateNextSceneTurnAsync` и `GenerateNetworkSceneTurnAsync`; различается в основном показ потокового предпросмотра, а не в доменной операции.
5. В `mobile/app/index.tsx` обычный чат и `ScenesScreen` отдельно реализуют опрос, начальную прокрутку, ленту, дату-разделитель, клавиатуру и управление кнопками.

## Риски текущей структуры

| Приоритет | Риск | Почему он возникает | Предлагаемая защита |
|---|---|---|---|
| Высокий | Два планировщика сцены | Desktop и сетевой путь создают собственные циклы автоматических ходов. | Один серверный `ConversationTurnRunner`; интерфейсы только отправляют команды. |
| Высокий | Регрессия функций | Исправление чата не переносится в сцену и наоборот. | Общий поток сообщений, общий API и общий компонент ленты. |
| Средний | Рост `MainViewModel` и `MainWindow.xaml` | В файлах уже сосредоточены генерация, навигация, редакторы, синхронизация и состояние UI. | Выделить application services и небольшие ViewModel/контролы по экрану. |
| Средний | Сложная Mobile-поддержка | Один `mobile/app/index.tsx` содержит список, навигацию, формы, профиль, сцену, опрос и визуализацию. | Разделить на screens, hooks и reusable conversation components. |
| Средний | Два поколения моделей | В проекте одновременно присутствуют ранние `AppData` / `CharacterProfile` / `ChatMessageRecord` и текущие `SoulDataRoot` / `SoulCharacter` / `SoulMessage`. | Зафиксировать текущий домен как единственный и удалить legacy-код после проверки отсутствия ссылок. |
| Низкий, но растущий | Цельный JSON-файл | Любая мутация сериализует весь `soulexe.json` под одним semaphore. | Пока оставить как надёжное портативное хранилище, но подготовить репозиторий разговоров и измерить размер/время записи до перехода на SQLite. |

## Целевая модель

### 1. Единый разговор

```text
Conversation
├── Id, Name, IsPinned, IsArchived, CreatedAt, UpdatedAt
├── Kind: Direct | Scene
├── Participants[]
├── Messages[]
├── Context: стартовые факты, summary, память, состояние
└── Policy
    ├── DirectConversationPolicy
    └── SceneConversationPolicy
```

`Conversation` отвечает только за то, что общее для любого разговора. У него не должно быть полей вида `CharacterAId`, `CharacterBId`, `UserProfile`, `DelaySeconds` одновременно в одном плоском классе.

### 2. Участники вместо специальных полей A/B

```text
ConversationParticipant
├── Id
├── Kind: User | Character | Director
├── CharacterId?                 // только для Kind=Character
├── DisplayName
├── SortOrder
└── CanGenerate
```

Обычный чат будет содержать пользователя и одного персонажа. Сцена — двух персонажей и, при необходимости, виртуального режиссёра. Это позволит позже создать групповой разговор, добавить NPC или дать пользователю роль в сцене без третьей модели данных.

### 3. Единое сообщение

```text
ConversationMessage
├── Id, SequenceNumber, CreatedAt, EditedAt
├── AuthorParticipantId?
├── Kind: Message | DirectorEvent | SystemEvent
├── Content / Variants[] / CurrentVariantId
└── Attachments[]
```

Обычное пользовательское сообщение — это `Kind=Message`, автором является пользователь. Сообщение персонажа — `Kind=Message`, автором является персонаж. Режиссёрское событие — `Kind=DirectorEvent`, а не отдельный класс сообщения. Так сцена сохраняет своё особое оформление, но получает редактирование, варианты ответа и вложения на тех же правилах, что и чат.

### 4. Политика разговора вместо второго движка

| Политика | Обычный чат | Сцена |
|---|---|---|
| Кто отвечает | Выбранный персонаж | `NextParticipantId` среди ИИ-участников |
| Режим запуска | Ответ на действие пользователя или «Продолжить» | Ручной ход либо автоматический таймер |
| Контекст | Персона пользователя, память, состояние, лор | Сценические рамки, общий Summary, участники, лор |
| Промпт | Базовые правила + политика direct | Базовые правила + политика scene |

Базовый построитель контекста должен стать общим `ConversationContextBuilder`. В него передаются сообщение, участники, память, лор и история. `DirectPromptPolicy` и `ScenePromptPolicy` добавляют только свои специальные системные инструкции.

## Что не нужно объединять принудительно

Не все различия являются ошибкой. Сцене действительно нужны `NextParticipantId`, режим чередования, задержка, статус выполнения и режиссёрские события. Обычному чату полезны настройки стартовой личности пользователя, варианты перегенерации и персональная память. Их следует хранить как **опциональные настройки политики**, а не терять ради внешнего единообразия.

Аналогично, UI одной ленты не означает одинаковый композер: в прямом диалоге важны «действие» и отправка, в сцене — пауза, режиссёрское событие и следующий ход. Общими должны стать модель, лента, форматирование, прокрутка и синхронизация; кнопки действий остаются конфигурацией режима.

## Безопасный план рефакторинга

### Этап 0. Защитить текущую версию

Текущий `main` остаётся стабильным. Работа выполняется только в `testing`. Перед миграцией нужны резервная копия `SoulExeData`, набор JSON-фикстур с реальным обычным чатом и сценой, а также проверка, что после импорта количество разговоров и сообщений совпадает.

### Этап 1. Ввести общий слой без смены хранилища

Добавить `ConversationSnapshot`, `ConversationParticipant`, `ConversationMessage` и интерфейс `IConversationRepository`. Создать два адаптера чтения:

| Адаптер | Источник | Результат |
|---|---|---|
| `ChatConversationAdapter` | существующий `SoulCharacter.Chats` | Conversation с пользователем и одним персонажем |
| `SceneConversationAdapter` | существующий `SoulDataRoot.Scenes` | Conversation с двумя персонажами и сценической политикой |

На этом этапе старые JSON-модели не меняются. Можно построить общий список разговоров и тесты, не рискуя историей.

### Этап 2. Унифицировать операции и генерацию

Создать application service `ConversationService` для базовых действий: создание, переименование, закрепление, архивирование, добавление сообщения, выбор варианта, выдача последних сообщений. Создать один `ConversationTurnRunner` для генерации, который принимает `ConversationId` и стратегию. UI и HTTP API не должны сами запускать циклы генерации.

### Этап 3. Миграция данных с обратимой схемой

Поднять версию JSON-схемы и выполнить миграцию только после прохождения тестов:

1. Сохранить автоматический backup исходного JSON.
2. Создать `Conversations` на верхнем уровне данных.
3. Перенести существующие GUID сообщений и разговоров без изменения текста и времени.
4. Временно оставить старые поля в режиме read-only compatibility.
5. При запуске выполнить проверку инвариантов: число чатов, сцен и сообщений до/после миграции.

Нельзя заменять существующие типы «на месте» без промежуточного адаптера: это опасно для сохранённых историй и Mobile API.

### Этап 4. Новый API с обратной совместимостью

Добавить `/api/conversations` и `/api/conversations/{id}`. В нём возвращать единый DTO с `kind`, `participants`, `messages`, `capabilities` и `turnState`. Старые `/api/chat` и `/api/scenes` оставить как адаптеры на один или два релиза, чтобы старые Mobile APK не перестали работать.

### Этап 5. Windows UI

Сначала перевести общий список, общую ленту сообщений, поиск, форматирование, прокрутку и инспектор разговора. Затем вынести сцено-зависимые кнопки и панель настроек в `SceneConversationControls`. Большой `MainWindow.xaml` следует разбить как минимум на `ConversationListView`, `ConversationThreadView`, `ConversationInspectorView` и `ScenePolicyEditorView`.

### Этап 6. Mobile UI

Разделить `mobile/app/index.tsx` на небольшие экраны и hooks:

```text
screens/conversations/ConversationListScreen.tsx
screens/conversations/ConversationThreadScreen.tsx
components/conversation/MessageList.tsx
components/conversation/ConversationComposer.tsx
hooks/useConversationList.ts
hooks/useConversationSync.ts
hooks/useConversationScrollAnchor.ts
```

В `ConversationThreadScreen` общими должны быть `FlatList`, дата-разделители, форматирование, initial scroll, сохранение позиции чтения и реакция на клавиатуру. Режим direct/scene передаёт только описание заголовка, действия композера и правила рендеринга автора.

### Этап 7. Удаление старых путей

Только когда Windows, Mobile и встроенный веб-клиент используют новый контракт, следует удалить `SceneService` как отдельное хранилище, старые раздельные DTO и неиспользуемые ранние `AppData` / `CharacterProfile` / `ChatMessageRecord`.

## Тесты, которые обязательны до миграции

| Сценарий | Проверка |
|---|---|
| Обычный чат | Импортирует пользователя, одного персонажа, варианты ответа, память и время сообщений без потери данных. |
| Сцена | Импортирует двух персонажей, режиссёрские события, Summary, следующий ход, задержку и статус. |
| Контекст | Общий builder не добавляет действия другого участника и сохраняет правила direct/scene. |
| Генерация | Один вызов «следующая реплика» создаёт ровно одно новое сообщение; два интерфейса не запускают две генерации. |
| Синхронизация | Изменение с Mobile появляется в Windows и обратно без сброса ручной прокрутки. |
| Совместимость | Старый Mobile API продолжает читать и отправлять сообщения через адаптеры. |
| Откат | При ошибке миграции автоматически восстанавливается backup и старые данные остаются читаемыми. |

## Первый практический шаг

Не стоит начинать с переписывания экранов. Самый безопасный первый коммит в `testing`:

1. Добавить новые read-only типы `ConversationSnapshot` и `ConversationMessage`.
2. Реализовать два адаптера чтения поверх текущих `SoulChat` и `SoulScene`.
3. Написать unit-тесты для преобразования обычного чата и сцены.
4. Не менять JSON-схему, UI, API и генерацию.

Этот шаг покажет, действительно ли выбранная единая модель покрывает текущие данные, но оставит возможность моментально отказаться от эксперимента без потери рабочей версии.

## Дополнительные улучшения после объединения

После появления общего домена будет безопасно заняться следующими задачами:

| Улучшение | Почему лучше делать после общего домена |
|---|---|
| Пагинация старой истории | Один способ получать страницы сообщений для всех разговоров. |
| Настоящий push/события вместо постоянного опроса | Один поток `ConversationChanged` для Windows, Mobile и веб-клиента. |
| Групповые разговоры и NPC | Участники уже представлены списком, а не парой `A/B`. |
| Одинаковые варианты, вложения и редактирование | Одна модель сообщения вместо отдельных `SoulMessage` и `SoulSceneMessage`. |
| Оптимизация хранилища | Репозиторий разговоров изолирует UI от будущего переноса JSON в SQLite. |

## Решение, которое предлагается принять

**Рекомендуемый вариант:** утвердить общую модель `Conversation` и начать только с read-only адаптеров и тестов в `testing`. После демонстрации преобразования на реальных фикстурах решить, переходить ли к миграции данных и API. Это избавит проект от накопившегося разделения, но не создаст риск одномоментного переписывания всего SoulExe.
