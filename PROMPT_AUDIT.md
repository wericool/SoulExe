# Аудит промптов SoulExe

## Карта путей

| Путь | Сборщик | Назначение |
| --- | --- | --- |
| Личный разговор | `ConversationPromptEngine.BuildDirect` | Ответ персонажа, включая выбранную персону или режиссёра. |
| Групповой разговор | `ConversationPromptEngine.BuildScene` | Ход одного AI-участника. |
| Продолжение ответа | `ConversationTurnRunner` + `ContinuationDirectorCommand` | Ещё одна реплика того же персонажа. |
| Summary личного разговора | `ChatSummaryService` | Краткая подтверждённая история. |
| Summary группового разговора | `SceneService.UpdateSummaryAsync` | Краткая общая история. |
| Soul Memory | `SoulMemoryService` | Маршрутизация памяти, тематическая память и дневник. |
| Генерация карточки | `CharacterCardGenerationService` | Поля или JSON карточки персонажа. |
| Транспорт LLM | `LlamaServerService` | Отправка сообщений в llama.cpp. |

## Найденные повторы и риски

1. Правило «не показывать рассуждения / `<think>`» находится и в ролевых форматах `PromptRules`, и в добавляемом транспортом `[DIRECT RESPONSE MODE]`. Второе правило меняет уже собранный промпт и может вытеснить полезный контекст.
2. Личный и групповой режимы имеют два похожих, но самостоятельно развивающихся правила форматирования. Общая часть должна жить в одном фрагменте; различия — быть короткими дополнениями.
3. `BuildLoreContext` поддерживает триггеры, порядок и лимиты токенов, тогда как `BuildSceneLore` берёт только постоянные записи и не ограничивает объём. Это не дублирование текста, но расхождение одной политики.
4. Summary и Soul Memory используют отдельные целевые промпты — это нормально. Их нельзя смешивать с промптом ответа персонажа; для них нужны отдельные snapshot-тесты, а не общий шаблон.

Статус: расхождение лора устранено. Оба режима используют `BuildLoreContext`; для группового разговора ключи проверяются по четырём последним репликам, а для личного — по трём последним репликам и текущему вводу.

## Целевой порядок промпта ответа

1. Глобальный режим ответа.
2. Системный preset и правила формата.
3. Карточка активного персонажа, выбранная персона пользователя и контекст разговора.
4. Состояние, лор, summary и долговременная память.
5. Блок языка ответа.
6. Обрезанная по бюджету история.
7. Явное новое сообщение пользователя либо инструкция следующего хода.

Пункты 1–7 должны формироваться в `ConversationPromptEngine`. Транспорт лишь проверяет лимиты, сериализует и отправляет уже готовый список сообщений.

## Идеи, независимо подтверждённые при изучении Soul-of-Waifu

Код Soul-of-Waifu не переносится: он GPL-3.0. Ниже только самостоятельные технические выводы для уже существующих возможностей SoulExe.

### Высокий приоритет

1. **Бюджеты по типам контекста.** Сейчас SoulExe считает общий размер системного блока, а затем оставляет место истории. Нужен общий `ContextBudgetPlan`: отдельный максимум для правил/карточки, состояния, лора, summary, памяти и истории. Самое важное — гарантированный минимум для последней истории и нового сообщения. Это предотвратит ситуацию, когда большой лор или summary фактически выключает память недавнего диалога.
2. **Единый выбор лора в обоих режимах.** Личный разговор умеет ключевые слова, вероятности и лимиты записи; групповой берёт только постоянные записи и без `TokenBudget`. Следует вынести selector в общий сервис. В запрос для ключевых слов безопасно включать последнее сообщение и короткое окно последних реплик, а не только текущий ввод.
3. **Структурированный trace промпта.** Нужен не только итоговый текст, а список блоков: источник, ориентировочные токены, лимит, причина включения и причина отсечения. Отображать его только в отладочном окне и маскировать содержимое по умолчанию.

### Средний приоритет

4. **Совместимость ролей с chat template.** В истории SoulExe режиссёр остаётся сообщением `system`. Это семантически верно, но не каждый шаблон llama.cpp одинаково обрабатывает системные сообщения посередине диалога. Нужен тест на фактическом выбранном chat template; если потребуется адаптер, режиссёр должен передаваться как явно размеченная инструкция, а не терять свой тип.
5. **Прозрачный порядок блоков.** Пользовательский preset должен явно объявлять допустимый порядок крупных блоков, но сам не должен иметь возможности выкинуть обязательные безопасность, язык или состояние. Это полезнее, чем свободная подстановка текста.
6. **Точные оценки токенов.** Текущий расчёт SoulExe — осознанная консервативная оценка для кириллицы. Позднее можно добавить опциональный локальный токенизатор выбранной модели, но fallback-оценка обязана остаться, чтобы не создавать новую тяжёлую зависимость.

Статус: есть первый исполняемый snapshot в `SoulExe.ConversationChecks`. Он проверяет личный разговор с автором-персоной, режиссёрским событием и лором, активированным недавней историей. Следующие сценарии — групповой разговор, summary и Soul Memory.

Статус: добавлен и snapshot группового разговора. Локальный лог обоих режимов теперь содержит одинаковые метаданные и диагностические причины без preview текста пользователя.

`ChatSummaryService` теперь использует чистый `SummaryPromptBuilder`, который покрыт snapshot-тестом. Это отделяет текст промпта summary от JSON-хранилища и позволяет менять его без риска незаметно изменить сохранение данных.

Все три промпта Soul Memory — Router, Archivist и дневник — вынесены в `SoulMemoryPromptBuilder` и покрыты snapshot-тестами. Их фоновые парсинг, расписание и атомарное сохранение при этом не менялись.

Устаревшие фасады `PromptEngine` и `ScenePromptEngine` удалены. Контракты промпта находятся в `PromptModels.cs`, а `ConversationPromptEngine` — единственный сборщик промптов ответов персонажей.

`ContextBudgetPlan` ограничивает лор, summary и карточки в обоих режимах, а также Soul Memory в личном разговоре. Превышения summary, памяти и карточки фиксируются диагностикой и проверяются snapshot-тестами; правила формата остаются следующим кандидатом для такой же защиты.

### Не переносить

- Превращение старых системных событий в сообщения пользователя ради шаблона без отдельной политики: это способно ослабить роль режиссёра.
- Автоматическую семантическую память как обязательную зависимость: она полезна только после измерения качества текущего `SoulMemoryService` и стоимости локальной embedding-модели.
- Длинные «всегда выводи JSON» инструкции для всех чатов: строгие протоколы нужны только состояниям и сервисным операциям, иначе они мешают естественному диалогу.
